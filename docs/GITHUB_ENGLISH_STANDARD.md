# IMPERIAL Core — GitHub English Language Standard

**Applies to:** First-party IMPERIAL Core GitHub engineering and public profile repositories.
**Effective:** October 29, 2026. **Owner authority:** Alexander Romaskevich (RomaskevicH).

## Canonical rule

Use **English only** in actively maintained GitHub README files, development guides, issue and pull-request templates, architecture explanations, CI labels, end-user instructions hosted in GitHub, and release notes. Keep canonical brand and software identifiers exactly as established, including **IMPERIAL Core, CAPITAL CORE, VELION, HANTER, ORION, LEGION, Nano Core Agents, CONSTRUCTOR AI, CYBER HAK, CRM-SOFFT, AI Passport, Enterprise Skills, Guardian Core, Approval Gateway, Audit Ledger, Zero Trust and CRYPTO IMPERIAL Ecosystem Boundary**.

The runtime model is **Federated Multi-Orchestrator Architecture**, not a single unrestricted global operational orchestrator. Do not rename established products or change technical behavior for a language-only update.

## Localization boundary

- **GitHub current first-party documentation:** English.
- **Official project and founder websites:** multilingual localization remains supported as separate, explicitly language-tagged routes.
- **Founder identification in GitHub prose:** use `Alexander Romaskevich` and `RomaskevicH`. Romanized variants are appropriate where necessary; full non-English text belongs on the multilingual sites, not in active technical README files.
- **Historical Git history and third-party source mirrors:** preserve original attribution, licensing, commits, examples and machine-readable interfaces. Do not rewrite historical commits or silently alter imported upstream code. An original third-party `README-ZH.md` is upstream content, not an IMPERIAL Core first-party language choice.
- **Compatibility paths:** existing historical filenames (for example `*_RU.md` for SHPAIZMAN) may remain to avoid broken backlinks, while their current contents are written in English. Any rename requires an explicit compatibility migration.
- **Production code and user interfaces:** translate text only with functional tests and expected-language requirements. Do not silently change API contracts, UI localization files, test fixtures, checksums or legal evidence.

## Engineering evidence standard

No change to the language of a README, a CI pass, a signed source hash or a status badge is evidence of actual production deployment, licensing, income, customer acceptance, model training, or global autonomous operations. Preserve **Architecture -> Implementation -> Evidence**, Zero Trust and the Public / Private Boundary.

New language fixes must be tested for valid Markdown links, original citations, accurate legal meaning and broken integration references. Do not disclose private client data or secrets in translation. Cross-border legal documents require jurisdiction-specific qualified review before legal reliance.

## Operational boundary

This document introduces **no scheduled automation, monitoring job or background check**. Future recurring audits require explicit owner authorization.
